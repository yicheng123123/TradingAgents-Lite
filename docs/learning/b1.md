# B1 学习笔记：一次任务如何完成模型调用与结算

这份文档沿着一条真实任务链路解释 B1-M 和 B1-E。目标是能自己追踪状态、API 请求、工具结果、Pydantic 校验和失败去向。文中的行号对应当前仓库源码。

## 1. 一次任务的调用链

入口是 tradingagents_lite/cli.py 的 main。用户运行 talite b1 后，CLI 把 scope、冻结任务路径、行情快照、A0.5 证据、B0 路径和输出目录传给 tradingagents_lite.b1.run_b1。

run_b1 先检查 Development 任务、行情 manifest、Evidence manifest 和 Evidence JSONL 的 SHA-256。Smoke 固定 dev-01 / AAPL 与 dev-02 / MSFT；全量 Development 是 20 题，不能传入其他任务集。随后校验 B0 归档与成本上限。没有 TALITE_API_KEY 时只产生 blocked 报告，不发模型请求。配置齐全后，代码按顺序运行 B1-M、B1-E，两个条件拿到同样的 model config 和 Budget；差异只有 B1-E 多绑定一个 cutoff 过滤的 financial_evidence 工具。

每个条件进入 tradingagents_lite.runner.run。Runner 每道任务单独创建 backend 和 LangGraph State，先构造当时可见的 MarketView，可选地再构造 EvidenceView，然后调用 build_workflow(...).invoke。Agent 图结束后，Runner 才调用 market.outcome 结算未来价格。模型工具本身没有 outcome 接口。

B1 任务链如下：

1. CLI 解析命令和 frozen paths。
2. B1 协调器核验输入哈希、预算并写 manifest。
3. Runner 为每道题建立独立 State。
4. Market Analyst 收到任务 prompt 和当轮 tools。
5. 模型返回 JSON 文本或 Function Call。
6. 本地执行器校验参数、运行绑定好的行情/证据方法，并写回 tool message。
7. Analyst 输出 MarketReport；Trader 只收到该报告引用的 evidence。
8. Pydantic 校验 Proposal，Risk Manager 执行固定波动率规则。
9. Runner 独立结算，记录逐题状态、token、耗时、Alpha 和错误。
10. B1 汇总 M/E 两组的逐题配对差异。

## 2. Agent State 在节点间如何传递

State 定义在 tradingagents_lite/workflow.py:90。当前关键字段如下：

| State 字段 | 谁写入 | 谁读取 | 用途 |
|---|---|---|---|
| messages | prepare、tools | analyst、backend | OpenAI 对话历史；工具输出以 role=tool 追加 |
| pending | analyst | tools | 待执行的模型 Function Calls |
| evidence | prepare、tools | analyst 校验、Trader | 当前任务实际观察到的数据，按 evidence_id 索引 |
| rounds | prepare、analyst | analyst | 限制分析师工具循环 |
| tool_trace | prepare、tools | Runner 汇总 | 记录工具名、参数、成功/错误和证据 ID |
| report | analyst | trader | 经 schema 与证据引用校验的 MarketReport |
| proposal | trader | risk | 经 schema 与证据引用校验的 Proposal |
| structured_output_trace | analyst、trader | Runner 汇总 | 记录 JSON/schema 是否有效 |
| citation_trace | analyst、trader | Runner 汇总 | 记录引用、有效 ID、无效 ID 和金融证据 ID |
| errors | analyst、trader | risk、Runner | 保留模型、结构化输出或工作流错误 |
| decision | risk | Runner | 最终 buy / sell / hold 及风险否决 |

这是每道任务在内存里的状态，不会跨任务共享。trajectory JSONL 保存审计需要的 state 摘要、最终 report/proposal、证据和工具轨迹；API 原始密钥不会进入 State。每次请求的 messages/tools 哈希存在 llm_calls 内，原始隐藏 reasoning 不写日志。

## 3. LLM 请求与 Function Calling

ModelBackend._call 负责 OpenAI-compatible Chat Completions 请求。请求包括 model、messages、temperature、max_tokens，以及当轮工具 schema。GLM-5.3 会明确设置 thinking enabled 和 reasoning_effort low。工具存在时 tool_choice 为 auto。

每个请求先计算：

- messages 的 prompt_sha256；
- tools 的 tools_sha256；
- 包含参数的 request_sha256；
- UTF-8 请求输入大小。

如果 messages + tools 超过 32 KiB，会在网络请求前失败。这样能给 smoke 成本估算一个保守输入上界。SDK 内部 retries 关闭，由项目自己的计数器实施一次有限重试。模型回复包含 tool_calls 时，provider 把函数名、参数和调用 ID 转成 workflow 可消费的结构。

Function Calling 不是模型直接运行 Python。模型只提出函数名和 JSON 参数；workflow 根据固定 registry 确认函数已注册，再用对应 Pydantic 参数模型校验，最后由本地执行器调用当前任务预先绑定的 MarketView 或 EvidenceView。Ticker 和 cutoff 不来自模型参数，因此模型无法要求执行器更换股票或查看其他历史日期。

工具完成后，执行结果以 role=tool 和原 tool_call_id 追加到 messages，下一次 Analyst 请求会同时看到原始任务、之前调用和新观察。工具错误也作为结构化观察返回，以便模型在尚有工具轮数时改用其他工具。

## 4. Structured Output 如何校验

Market Analyst 的最终 JSON 在 workflow.py:176-186 由 MarketReport.model_validate_json 校验。Schema 包括 view 和 evidence_ids。Schema 正确之后，workflow.py:193-200 再确认每个 ID 已经真实出现在当前 State 的 evidence 字典中。

Trader 的回答由 provider.py:154-161 解析为 Proposal，Proposal 的 action 是限定枚举；非法 action、缺字段和坏 JSON 都会抛出 Pydantic ValidationError。Workflow 接着在 workflow.py:241-248 校验 Trader 引用必须属于传入的证据。方向性 Proposal 还必须带有引用。

因此，“JSON 格式可解析”和“证据引用真实有效”是两种不同检查。metrics 会分别保留 structured_output_trace 与 citation_trace；某个任务任何阶段失败，都不会因为风险节点产出 fallback Hold 而被算成正常 Hold。

## 5. 失败、恢复与终止

- 工具参数不符合 schema：返回 invalid_arguments，不调用工具。
- 未注册的工具：返回 unknown_tool。
- 本地工具抛出 TimeoutError：转换成 tool_timeout，并留在工具轨迹中。当前工具均为同步本地读取；CPU 测试模拟异常路径，不提供通用的线程中断超时。
- 其他工具异常：只记录错误类型，不写入可能包含隐私的异常文本。
- 模型请求超时、连接失败、限流、HTTP 408 或 5xx：每个逻辑请求最多重试一次。其余 HTTP 错误不重试。
- 结构化输出解析失败或引用未知 ID：任务失败并记录阶段，不做自动 JSON 修复或第二次“重写答案”请求。
- Analyst 用尽两轮后，下一次请求不再附带 tools，只要求最终 MarketReport。
- 最终缺少有效 Proposal 时，Risk 节点会 fail closed 生成 Hold；Runner 仍将任务标记 model_error / workflow_error。该任务没有 Alpha，不会混入成功 Hold 的统计。

OpenAI SDK 超时设为 25 秒。远端可能已经处理超时请求，所以发生重试或错误时，如果无法获得所有请求的 usage，API 成本会标记 unknown；不根据收到的部分响应假装得到完整账单。

## 6. Token 使用量如何累计

每个成功 API 响应的 usage.prompt_tokens 和 usage.completion_tokens 累计到该任务 backend.usage。calls 计真实 HTTP 请求尝试数，logical_calls 计 Agent 的模型调用意图，retries 单独计重试数，failed_calls 记录最终失败。llm_calls 列表为每次尝试记录耗时、状态、模型响应 ID、实际返回模型名、token 用量和请求哈希。

Runner 汇总逐任务 usage，再计算输入/输出 token 总数和平均 API 调用延迟。仅当模型价格存在、所有请求都有 usage 且没有失败或重试时才生成可估价的成本值；遇到不完整 usage 或重试即报告 unknown。成本是官方价目表估算，不替代服务商账单。

## 7. 四个核心函数逐段阅读

### A. B1 协调器：tradingagents_lite/b1.py，run_b1（第 259 行）

**输入**：scope、任务文件、行情目录、Evidence 目录、B0 归档目录、输出目录、统计 seed 和可选预算上限。

**输出**：包含 status、结果目录、选中 task IDs、保守成本上限及阻塞原因的 dict；同时写出 manifest、summary.csv、REPORT.md 和两组运行目录。

阅读顺序：

- 第 242–261 行：固定 scope 和任务、行情、证据哈希；加载 EvidenceStore。
- 第 263–289 行：选择唯一 smoke pair，并确认 B0 对照确实运行在同一 20 题和快照上。
- 第 269–278 行：计算 worst-case 请求成本；完整 Development 未传预算或预算低于上限时停止。
- 第 291–327 行：固定模型 endpoint 和协议，并写入 run manifest。
- 第 335–354 行：没有 API Key 时记录明确的 blocked 结果，不产生模型指标。
- 第 355–409 行：使用同一个 client、模型和 Budget 顺序运行 B1-M 与 B1-E，再做逐题配对。
- 第 411–419 行：写最终汇总和报告。

**设计取舍**：输入 hash 校验提高了复现性，却要求任何数据变更都建立新实验协议。两个组顺序运行，节省并发复杂度，但服务端模型若在两组之间更新，必须依赖 API 返回模型名和运行时间发现。

**面试追问**：

1. 为什么只检查任务文件名不够，必须验证内容 hash？
2. 成本上限中的逻辑调用、HTTP 重试和输出 token 是如何推导的？
3. 如果服务返回的 model 名称为空或和请求不一致，结果应该怎么标记？

### B. LangGraph 状态机：tradingagents_lite/workflow.py，build_workflow（第 120 行）

**输入**：当前任务的 MarketView、Backend、Budget、是否启用 ReAct，以及可选 EvidenceView。

**输出**：一个编译好的 LangGraph，可通过 invoke 输入初始 State 并得到最终 State。

阅读顺序：

- 第 127–145 行：建立工具注册表；只有传入 EvidenceView 时才注册 financial_evidence，并校验函数参数。
- 第 147–160 行：创建每题的共同 system/user prompt 和初始 State。
- 第 162–200 行：调用 Analyst、处理有限工具调用、解析 MarketReport 并校验证据引用。
- 第 202–224 行：在本地执行已注册函数，把结果和 tool_call_id 写回消息。
- 第 226–248 行：只将已引用的证据给 Trader，校验 Proposal 及其引用。
- 第 250–274 行：执行 Risk gate，并声明图的节点和条件边。

**设计取舍**：把 MarketView / EvidenceView 通过闭包绑定到每个任务，可以让模型只选择“读什么”，而不能指定“读哪只股票、哪个时间”。代价是工具执行器目前是同步本地函数；未来接远程 MCP 工具时要增加真正可取消的超时、重试与权限隔离。

**面试追问**：

1. 如何证明 outcome provider 不在模型工具可达图里？
2. structured output 合法但 citation ID 未观察到时，为什么仍要失败？
3. 如果工具执行成功但模型之后输出坏 JSON，哪些结果应该保留，哪些指标不能计分？

### C. Provider 适配：tradingagents_lite/provider.py，ModelBackend._call（第 70 行）

**输入**：OpenAI message list 和可选 tool schemas。

**输出**：标准化 assistant message，内容可以是文本，也可以包含已经规范化的 tool_calls；usage 和每次网络尝试写在 backend 实例上。

阅读顺序：

- 第 71–83 行：设置工具、温度、token 上限和 GLM thinking 参数，再计算 request/prompt/tools hashes 与输入字节数。
- 第 84–92 行：登记逻辑调用；超出输入包限制时在联网前失败。
- 第 94–112 行：真实请求和暂时错误的一次重试；SDK 不会在内部再重试。
- 第 114–147 行：累积 token，校验响应形状，规范化函数调用并记录实际返回模型、耗时和哈希。
- 第 148–161 行：返回 Analyst 内容；Trader 接口随后用 Pydantic 解析 Proposal。

**设计取舍**：逐次调用应用层 retry 更容易复现和核算；重试也可能带来重复计费，因此失败或重试后的最终成本标为 unknown。请求只保存 hash 和摘要字段，不把 Key 或模型隐藏推理过程存进 artifact。

**面试追问**：

1. calls 与 logical_calls 为什么不是同一个计数？
2. API response 缺少 usage 时，为什么不能把成本设为 0？
3. 如何避免异常日志泄露 API Key，同时保留可诊断性？

### D. 评测和逐题归档：tradingagents_lite/runner.py，run（第 177 行）

**输入**：任务与行情路径、输出目录、backend factory、模型配置、Budget、统计 seed、是否 ReAct 和可选证据目录。

**输出**：逐题 trajectory、SQLite 账本、run.json、summary.csv、REPORT.md 与指标字典。

阅读顺序：

- 第 181–202 行：解析固定任务、加载 hash 校验的行情和 Evidence，并记录 Git SHA、依赖与 manifest。
- 第 203–220 行：创建新输出目录，对每个任务建立独立 backend 和 graph。
- 第 221–248 行：区分 model/workflow/runtime failure；只有 status=ok 的任务获得可评分 Alpha。
- 第 250–259 行：把每题记录写入 JSONL 和 SQLite，并复制出单独 trajectory 文件。
- 第 260–282 行：汇总指标、写报告，记录实际返回的模型名称。

**设计取舍**：失败任务可以保留一个方便下游处理的 fallback Hold，但 status 仍会让评分排除它。future outcome 仅由 runner 单独获取，因此代码结构上能测试 Agent 看不到结算值；历史行情供应商的修订和模型预训练知识仍是外部限制。

**面试追问**：

1. 为什么方向命中率只以非 Hold 作为分母，而 Coverage 另行报告？
2. 为什么 bootstrap 按 decision date 聚类？
3. 如果 SQLite 比 JSONL 多写了一行，如何恢复和审计？

## 8. 亲自完成的小型练习

在 tradingagents_lite/b1.py 的 _paired 函数中，加入一个按 ticker 分组的方向转变统计：buy→sell 和 sell→buy 各自计数。保持现有 paired_n 和 Alpha 差值定义不变。

你需要自己：

1. 决定哪些 task 可进入 paired 集；沿用 B1-M 与 B1-E 都成功且有结算的规则。
2. 增加至少两个 CPU 测试：一题 buy→sell、一题 sell→buy；另加一个失败任务确认它不会进入配对分母。
3. 验证空配对输入返回明确的 0 / null，而不是除零异常。
4. 运行 uv run --locked pytest -q tests/test_b1.py 和完整 uv run --locked pytest -q。
5. 对照 paired_summary.json 的含义，确认这个方向转变计数不改变 Alpha 统计。

练习只针对诊断输出，不修改冻结数据、历史结果或模型协议。
